# Agentic EBS — 網頁 App

[English](README.md)

單機靜態網頁，資料直接存放在指定的本機資料夾。無後端、無安裝。

專案總覽與設計理由見上層 [README](../README.zh-Hant.md)；本文是操作說明。

## 執行需求

- Chrome 或 Edge（使用 File System Access API，**不支援 Firefox / Safari**）。
- 任一靜態 HTTP 伺服器。**不能**以 `file://` 直接開啟 `index.html`，File System Access API 需要 localhost 或 https。

```
cd App
python -m http.server 8765
```

瀏覽器開啟 <http://localhost:8765>。沒有 Python 時任何靜態伺服器皆可，例如 `npx http-server -p 8765`。

## 第一次使用

1. 點右上「選擇任務資料夾」，在開發專案下新建一個空資料夾指定給它。工具會自動建立 `settings.json`、`calendar.json`、`prompts/`、`tasks/`。
2. 首次連結會自動開啟設定頁。上面有兩欄帶標記——「任務資料夾相對路徑」與「Git 使用者名稱」——兩者都影響 agent 的分析品質，而且填錯或留空都不會有錯誤訊息，填法見 [設定頁](#設定頁)。
3. 之後重新整理會自動記住資料夾。瀏覽器要求重新授權時，點一下「重新連結任務資料夾」即可——授權需要使用者手勢，無法自動完成。

資料夾放在開發專案內或外皆可，prompt 使用的是相對於開發專案的路徑。建議放在專案內，多數 CLI agent 預設不存取工作目錄以外的位置；代價是記得將資料夾加進該專案的 `.gitignore`。

## 一張任務卡的完整操作

1. 在首頁輸入標題建卡。建立後會直接進入任務頁並詢問是否**立即開工**；選擇開工，計時即從此刻起算。接著按「需求描述」的 ✎ 撰寫需求，寫得越細，後續分析越準確。

   > 釐清需求本身就是這張卡的工作，因此計時從這一刻開始，而不是等到動手寫程式。建卡時選擇取消也無妨，之後隨時可按左側的「開工」補上。

2. 按「複製 Prompt」，貼給在開發專案目錄下執行的 agent。prompt 會自動帶入設定頁填寫的任務資料夾相對路徑，agent 依該路徑讀寫任務資料。
3. agent 先產出 `understanding.md`，列出採用的假設與待釐清的問題後停下等待確認。需求對齊之後才續產 `approaches.md` 與 `estimate.json`。回到網頁重新整理即可看到解法分析與校正後的分佈。
4. 與 agent 討論並選定要採用的解法；不滿意可請它繼續修改。
5. 勾選解法之後，同一個區塊標題列上的「複製步驟卡 Prompt」才會解除停用。貼給 agent 產出 `steps.md`，再按「實作步驟卡」區塊上的「複製實作 Prompt」，把執行規則與步驟卡一併交給負責實作的 agent 逐張領取。建議這裡換一個乾淨的 agent，理由見下一節。
6. 實作定案、不再調整之後，複製「統整與收尾」的 prompt。agent 會依最終的程式碼產出 `final-spec.md`、`spec-diff.md`、`logic.md`。趁卡片仍在計時中進行——收尾同樣是工時。
7. 交付後按「完工」。

被緊急任務插斷時，直接開始另一張卡即可，原卡會自動讓位並在緊急卡完成後恢復。被會議或雜事打斷則不需暫停計時。

## 分析與實作交給不同的 agent

三個階段各有獨立的規則書（`analyze-task.md`、`steps-guide.md`、`implement.md`），本來就是分開設計的。

負責分析的 agent 走到步驟卡階段時，已經累積了大量需求討論的脈絡，繼續讓它實作會擠壓 context。換一個乾淨的 agent 只讀步驟卡，反而更專注。附帶的好處是實作若走偏，回頭找分析 agent 討論時，它的判斷還沒有被實作細節污染。

步驟卡本身也是為此設計的——每張卡可獨立領取，實作 agent 不需要讀完整個討論過程。

## 設定頁

### 資料夾與路徑

| 欄位 | 說明 |
|---|---|
| 任務資料夾 | 顯示目前連結的資料夾名稱，旁邊的按鈕可隨時更換。換資料夾等於換一整套歷史，velocity 池不會跟著走 |
| 任務資料夾相對路徑 | 同一個資料夾在 agent 眼中的位置，相對於**開發專案** |

這兩欄指的是**同一個資料夾**，但回答的是兩個不同的問題：
- 前者是「瀏覽器要讀寫哪個資料夾」
- 後者是「agent 在終端機裡要怎麼走到它」

之所以不能自動推導，是因為瀏覽器基於安全限制**拿不到資料夾的絕對路徑**。網頁既不知道資料夾在磁碟上的位置，也不知道開發專案在哪，所以這條路徑只能由使用者告知。

首次連結時預設帶入資料夾名稱，資料夾直接放在專案根目錄下就已經是對的；其餘情況要自行修正：

| agent 執行的開發專案目錄 | 資料夾實際位置 | 「任務資料夾相對路徑」要填 |
|---|---|---|
| `~/code/MyGame` | `~/code/MyGame/ebs-data` | `./ebs-data`（預設值即正確）|
| `~/code/MyGame` | `~/code/MyGame/docs/ebs-data` | `docs/ebs-data` |
| `~/code/MyGame` | `~/code/ebs-data` | `../ebs-data`（agent 需有存取上層目錄的權限）|

填錯不會有任何錯誤訊息，agent 只會回報找不到檔案。

### 工作時間

決定「一段計時區間裡有多少算工時」。落在時窗外的時間（夜間、休假）預設計 0。

| 欄位 | 說明 |
|---|---|
| 時區 | IANA 時區名稱，預設取瀏覽器時區。所有日期鍵都經它換算 |
| 上班 / 下班時間 | 每日工作時窗 |
| 工作日 | 勾選週幾算工作日，未勾選者視為休假 |
| 休息時段 | 不計入工時的區間，可多段，預設含午休 |
| 工作日曆 | 摺疊的編輯器，逐日覆寫該天的上下班時段（工時由時段推導，不是直接填數字）。即改即存，而且會**回溯**影響那一天已計入的工時與 velocity |

**在午休或下班後工作，那段時間算不算？**

預設不算。但如果「開工」或「完工」正好按在那段時間裡，工具會把它列出來詢問——按下按鈕的那一刻人確實在場，那段時間有證據。以上班 09:00–18:00、午休 12:00–13:00 為例：

| 情境 | 這張卡當天算幾小時 | 工具行為 |
|---|---|---|
| 12:30 開工，18:00 完工 | 5 小時（13:00–18:00）| 會問 12:30–13:00 這半小時要不要加進來 |
| 11:00 開工，14:00 完工，中午沒關錶就去吃飯 | 2 小時（11–12、13–14）| 不問。12:00–13:00 夾在中間，沒有在場證據 |
| 21:00 開工，23:00 完工 | 0 小時 | 會問這整段 2 小時要不要計入 |
| 週五 17:00 開工，忘了按完工，週一 10:00 才關錶 | 2 小時（週五 17–18、週一 9–10）| 不問。週末整段夾在中間 |

工具什麼時候會來問、以及確認的先後順序，見 [工作日曆與工時確認](#工作日曆與工時確認)。

### Git

| 欄位 | 說明 |
|---|---|
| Git 使用者名稱 | 姓名或 email。agent 以 `git log --author=<這個值>` 過濾出本人的 commit，用來了解慣用做法與改動規模。**留空不會報錯，但過濾條件失效**，agent 讀到的是整個團隊的歷史 |

### Prompt 客製化

| 欄位 | 說明 |
|---|---|
| 產出語言 | agent 撰寫任務文件與對談時使用的語言，填語言名稱即可，留空等於英文。詳見 [介面語言與產出語言](#介面語言與產出語言) |
| Prompt 編輯器 | 資料夾內每個 prompt 檔各有一組編輯框，可獨立儲存或還原預設 |

## 工作日曆與工時確認

`calendar.json` 只記錄被確認或修改過的日子。**其餘日子不寫任何資料**，工時直接依設定頁的工作時窗計算，假日算 0，狀態一律視為「未確認」。首頁會列出**與計時區間重疊、且尚未確認的過去日子**——沒有任務在跑的日子不會來打擾。

確認分兩階段，有先後順序：

1. **當天實際的上下班時間。**
2. **落在工作時窗之外、且緊貼計時區間起點或終點的那段時間。** 由使用者裁決要不要計入。夾在區間中間的窗外時間不問也不計，判準與實際例子見 [工作時間](#工作時間)。

順序不能顛倒。時窗尚未定案就先裁決窗外工時，時窗一旦修改，先前的裁決就得重來。

未確認的日子不會擋住任何操作，但**跨越這些日子的完成卡不會進入 velocity 統計池**，卡片上會標示原因。

任務頁另外顯示一個「實際經過時間」，那是區間的純長度，不扣時窗也不計入 velocity，只供對照。

## 手動增修計時區間

任務頁的「時間紀錄」區塊列出這張卡所有**已結束**的計時區間。每一列都能直接修改起訖時刻或整段刪除。

下方的「手動新增區間」會補上一段「一小時前到現在」，再自行改成正確的時間。結束時間早於開始時間會被擋下。

**進行中的那一段不能在這裡編輯。** 工具靠「全系統最多一段計時在跑」維持插斷堆疊的正確性，正在跑的區間只由「開工」「完工」兩顆按鈕控制。要修正它，先按「完工」關起來，改完再按「重新開工」。

### 該修時間的情境

| 情況 | 做法 |
|---|---|
| 忘記按「開工」，做了一小時才想起來 | 按下「開工」，再用「手動新增區間」補上先前那一小時 |
| 忘記按「完工」，掛著過夜或過週末 | 先按「完工」，再把該段的結束時間改回實際收工的時刻 |
| 誤按「開工」，其實沒有動工 | 按「完工」之後把那一段刪掉 |
| 在沒有開著網頁的環境做的（另一台機器、離線）| 用「手動新增區間」補上 |

### 不該修的情境（真實的膨脹）

開會、被同事叫住、臨時處理雜事——這些時間本來就該留在紀錄裡。velocity 存在的目的正是捕捉這種膨脹；一段段修掉它，等於刪掉工具唯一的訊號來源，估計只會越來越樂觀，而且看不出是怎麼壞的。

判斷標準：**這段時間人在不在**。
- 不在（睡覺、下班、根本忘了關錶）是紀錄錯誤，該修
- 人在、只是被別的事佔用，就留著。

若那件別的事大到值得單獨追蹤，正確做法是替它開一張新卡——原卡會自動讓位，時間各歸各的，不需要手動改任何區間。

## 任務分類（tags）

agent 會替任務卡標上分類，用途是讓下次分析優先參考「分類相近」的舊任務，不影響工時估算。

預設那幾個只是**預設值**。到設定頁 →「Prompt 客製化」→「② 分析規則」，把分類清單換成自己領域的詞彙即可（做遊戲的可換成 `gameplay`、`shader`、`level-design`），程式不檢查內容。但要維持**固定的一組詞**，別讓 agent 每次自由發明——同一個概念寫成 `frontend` 和 `front-end`，相近比對就失效了。

若此工具更新後升級了 prompt，已經被使用者改過的 prompt **不會**被升級覆蓋。升級逐檔比對內容 hash，只有「沒被動過」的檔案才自動更新；並在設定頁提示有新版可看，由使用者決定要不要採用。

## 介面語言與產出語言

頁首右上的下拉選單可切換語系，首次開啟依瀏覽器語言自動選擇，之後記在這個瀏覽器裡（不寫進資料夾）。

### 指示的語言與產出的語言

1. 給 agent 的 prompt（`prompts/`）一律英文、只有一份，那是**指示**的語言。
2. agent 用哪種語言寫任務文件、跟使用者對談，是設定頁的「產出語言」欄位，填語言名稱即可（`繁體中文`、`日本語`、`Traditional Chinese` 都行，留空等於英文），複製 prompt 時會自動附加一句指示。

存放位置不同也是刻意的：介面語言與主題存在瀏覽器（換電腦不跟著走），產出語言存在**資料夾**的 `settings.json`。後者決定寫進資料夾的內容，換一台電腦也該是同一種語言，否則同一個資料夾會長出兩種語言的歷史文件。第一次連結資料夾時會帶入當下的介面語言，此後兩者獨立。
