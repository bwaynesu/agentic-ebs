# Agentic EBS

[English](README.md)

**需求由開發者描述，任務拆解與估時交給 AI agent，實際工時由工具記錄；累積之後再以歷史偏誤，把 agent 的理想估計校正成機率分佈。**

給開發者使用的任務卡工具。單機靜態網頁，資料存放在指定的本機資料夾，沒有後端、沒有框架、沒有 build step，不對外傳送任何資料。

一張任務卡的完整流程：
```
1. 建卡並開始計時
2. 撰寫需求
3. agent 分析（需求理解 / 多種解法 / 理想工時）
4. 選定解法
5. agent 拆成實作步驟卡
6. 實作
7. agent 收尾產出文件
8. 完工
```

全程單一計時軌道，介面上只有「開工」與「完工」兩顆按鈕。

## 工具做什麼

建立任務卡並寫下需求後，任務頁會提供一段可直接複製的 prompt。將它交給任一能在專案目錄下執行的 AI agent（Claude Code 或其他 CLI agent），讓 agent 讀取開發者專案原始碼、git log 以及本工具累積的歷史任務，它將產出三份東西：

- `understanding.md` — 需求理解，列出採用的假設與尚待釐清的問題
- `approaches.md` — 多種解法，每種寫到「改哪個檔、加哪個函式、動哪個設定」的粒度
- `estimate.json` — 每種解法一個理想工時

開發者選定解法後，agent 進一步把它拆成可獨立領取的實作步驟卡。實作定案後再由 agent 依**最終的程式碼**產出收尾文件：最終規格、與原規格的差異及原因、程式運作邏輯。

計時由「開工」啟動、「完工」結束。撰寫需求、討論、等待 agent、實作、收尾都記在同一條軌道上。

任務卡累積之後，網頁以歷史 velocity（估計 ÷ 實際）把 agent 的理想估計換算成 P5 / P50 / P95 的機率分佈。

整體產出因此有三類：
1. 動手前強迫釐清問題的流程
2. 每張卡完整保留的前因後果
3. 一份隨使用次數逐漸貼近實際的估時

## 設計依據

做法沿用 Joel Spolsky 於 2007 年提出的 [Evidence Based Scheduling](https://www.joelonsoftware.com/2007/10/26/evidence-based-scheduling/)：不以主觀估計為準，而是記錄估計者過去的偏誤，再用該比例修正新的估計。EBS 的負擔在於它要求開發者持續拆解、估時、記錄工時，而本工具把這幾件事移交給 agent。

估計者由開發者本人換成 agent 之後會發生什麼，仍在觀察中。

三項刻意的設計：

1. agent 只估「不被打擾的理想工時」，不做自我校正。校正屬於 velocity 的職責，agent 若再調整一次即構成重複校正。

2. 被會議或雜事打斷時**不用暫停計時**。該膨脹正是 velocity 要捕捉的訊號。

3. 緊急任務採插斷堆疊，工時永遠只歸最上層的卡，且不需要額外操作——緊急卡的「開工」與「完工」本來就要按。

## 研究方向

當估計者從開發者本人換成「agent ＋ 一名負責審閱的人」，EBS 的假設是否仍然成立，是本專案想弄清楚的事。

工具留下的資料足以支撐幾個具體問題：

- velocity 的離散程度。散不會讓機制失效，但會讓輸出寬到無法用於決策；界線落在哪裡是實際問題。
- `estimate.json` 記錄了 `model` 與 `templateVersion`。更換 model 或大幅改寫 prompt，是否等同換了一個估計者。
- 步驟拆解的細緻程度與估計準確度的關係。`steps.md` 的步驟數是現成的自變數。
- 歷史脈絡的實際效益。每張卡都留著前因後果，新卡分析時 agent 讀得到——這些累積究竟讓估計變準了，或只是提高了主觀信心。
- 任務分類（tags）分池後，分佈是否更貼近該類任務。這需要每一類都累積足夠張數。

這些問題目前多半還沒有答案，其中幾個我也不確定問得夠準確。歡迎透過 issue 討論。

## 目前觀察

資料仍在累積，數字暫不公開。但有兩件當初不在設計目標內的效果，從第一張卡就開始發生。

### 由上而下的解題流程

需求描述 → 分析 → 選解法 → 步驟卡 → 收尾，任務頁由上往下走一遍，會迫使問題在動手之前被講清楚。這正好對應 Joel 所說 16 小時規則的真正用意，統計反而是附帶的。

### 每張卡保留的前因後果

understanding、approaches、steps 與收尾文件都留在卡內，數個月後仍查得到「當時為什麼選這個做法」。開新卡時 agent 也讀得到這些，等於每次分析都比上一次多知道一些。

### 尚未兌現的部分

velocity 與機率分佈還沒有真正的使用場合——目前的開發團隊，至今沒有人問過我某個任務要做多久……

工具目前的邊界：它計算的是**單張卡的耗時，而非一批卡的交付日期**。後者需要蒙地卡羅將多張卡加總（風險互相抵消），`ebs.monteCarlo()` 已實作並通過測試，但目前沒有任何呼叫端。輸出單位是小時。

## 執行環境

- 需要一個能在開發專案目錄下執行的 AI agent。此工具本身不呼叫任何 API，分析與實作全部依賴外部 agent。
- Chrome 或 Edge。本工具使用 File System Access API，**Firefox 與 Safari 不支援**。

> **備註：分佈需要時間才會準確，但不需事先準備任何資料。** 從第一張卡起即可正常使用；完成的卡累積到二十餘張之前，分佈會偏寬。那是預期行為，並非設定錯誤。

## 取得與執行

### 線上版

掛載於 GitHub Pages，開啟網址即可使用。（**待部署，網址之後補上**）

程式碼在網路上，資料留在本機——網頁不會上傳任何內容，也沒有可上傳的對象。

### 本機執行

Clone 專案或直接下載 `App/` 資料夾，然後：

```
cd App
python -m http.server 8765
```

開啟 <http://localhost:8765>。不能以 `file://` 直接開啟 `index.html`，File System Access API 需要 secure context。沒有 Python 時，任何靜態伺服器皆可，例如 `npx http-server -p 8765`。

## 首次設定

第一次在某個開發專案使用時，除了指定存放任務的資料夾之外，還要進設定頁完成幾項設定。其中兩項漏掉不會報錯，但會讓 agent 的分析失準，所以請務必照著走一遍。

**設定步驟、各欄位說明，以及一張任務卡從建立到完工的完整操作，請見 [App/README.zh-Hant.md](App/README.zh-Hant.md)。**

## 語言

介面語言可在頁首右上切換。

給 agent 的 prompt（`prompts/`）一律英文、只有一份，那是**指示**的語言，與 agent 的產出語言無關；產出語言在設定頁另外指定，填語言名稱即可。prompt 本身也可以在設定頁改寫成自己要的規則。

## 專案結構

```
App/            網頁本體（vanilla JS）
├── js/ebs.js       EBS 統計計算與工作日曆推導（純函式）
├── js/timer.js     計時與插斷堆疊狀態機（純函式）
├── js/tasks.js     任務卡資料邏輯：排序、id 生成、狀態文案（純函式）
├── js/i18n.js      UI 文字字典（繁中 / 英文）與 t()（純函式）
├── js/store.js     File System Access 存取層與 prompt 升級判斷
├── js/app.js       UI（區塊局部更新，不整頁重繪）
├── style.css       三檔主題（淺色 / 灰階 / 深色）與版面
├── prompts/        給 agent 的規則書與模板（初始化時複製到資料夾）
└── prompt-changelog.md
Docs/
├── data-format.md  所有 JSON schema 與規則（單一事實來源，英文）
└── design.md       現況的設計決策與理由（英文）
```

## 測試

```
node --test "App/js/*.test.mjs"
```

純函式皆有測試。`style.css` 有一組靜態契約檢查（三個主題的變數集合須一致、每個主題都要宣告 `color-scheme`、不得寫死色碼），`prompts/` 有篇幅預算與清單同步檢查。`app.js` 僅負責組 DOM，以 `node --check App/js/app.js` 做語法檢查。

不使用測試框架，只用 Node 內建的 `assert`。
